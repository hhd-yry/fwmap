fwmap 案例：在一个已饱和的目标上做零日猎取

Tenda AC15 V15.03.05.19 · 2026-11-08 · 结论：未发现新漏洞（负结果）
一句话：工具在这个从未见过的构建上排出 42 条候选链、覆盖 25 个函数；逐条人工复核并做公开库比对后， 24 个可达函数全部对应已公开 CVE，剩余 1 个是不可达的死代码。 这不是工具失败，而是目标已被 fuzz 饱和——报告的重点因此从「挖到了什么」转为 「如何证明一个目标已经没有零日可挖」，以及这轮暴露出的 4 个工具边界。

2. 方法：怎么判定「新不新」

静态分析只能说明「有数据从请求流到危险函数」，不能说明「没人报过」。所以本轮把新颖性判定做成了独立的一步：

#做法为什么必须这样
1NVD API 关键词检索 Tenda AC15，取全量 106 条，抽取描述里的函数名建索引先知道这个型号被报到什么程度
2对工具报出的每个函数，按函数名再查一次 NVD有些 CVE 是用别的型号报的，同源代码
3对每个函数，按路由名再查一次（如 SetDlnaCfg）关键补漏：有的公告只写路由不写函数名，第 2 步会漏掉
4对仍无命中的，回落到反编译人工判读（缓冲区大小、有无上界、有无 canary、是否可达）公开库没有 ≠ 不是漏洞，必须自己看代码
这一步踩过的坑（值得写进方法学）：第一版索引只匹配描述里的小写 form* / from*， 于是 formDLNAserver 看起来「无人报过」。改用路由名 SetDlnaCfg 一查， 立刻命中 CVE-2024-10661，且描述里的版本号就是 15.03.05.19。 函数名和路由名必须双路检索，否则会把复现误判成零日。

4. 三个案例：工具在哪一步对、哪一步错

4.1 精确命中：formDLNAserver（/goform/SetDlnaCfg）

工具报出「scanList → sprintf」，人工复核把边界算完整了：
char acStack_116c [4096];
local_28 = websGetVar(param_1, "scanList", "");
...
local_2c = strtok(local_28, "\t");              // 制表符分隔
iVar1 = sprintf(acStack_116c + local_18, "%s\n", local_2c);
local_18 += iVar1;                                  // 无任何上界检查
while ((local_2c = strtok(NULL, "\t"))) {           // 还能继续喂
    iVar1 = sprintf(acStack_116c + local_18, "%s\n", local_2c);
    local_18 += iVar1;
}
fwrite(acStack_116c, local_18, 1, local_1c);        // 越界长度也照样写
这轮从二进制里算出来的事实依据
缓冲区 4096，每条 token + "\n"反编译 + 定位 .rodata 里的 "%s\n" 与 "\t"
约 4100 字节的 scanList 即可越界累加偏移无比较
未开栈保护，溢出可直达保存的 LR二进制中无 __stack_chk_fail、无 stack smashing
附带越界读：栈内容被写进 dlna.dbfwrite 用溢出后的 local_18 当长度
公告（CVE-2024-10661）只写了缓冲溢出；「同一根因顺带泄露栈内存」这一点是我们自己补的。 这是负结果报告里唯一可算作增量观察的东西，但它不是独立漏洞。

4.2 被 M2 拦下的假线索：FUN_000a88a4 是死代码

doSystemCmd("behavior_manager %s --%s /etc/chengyanconfig/dem",
            modulename, option);      // 两个 HTTP 参数零过滤拼进 shell
只看 M3，这是标准的命令注入。但：
检查结果
M2 的 142 条 route→handler 里有它吗没有
Ghidra ListCallers 查调用者无调用者
数据引用（函数指针表）无引用
结论：死代码。这是分层设计价值最直接的证据——M2 的端点表能把 M3 的函数级误报按下去。

4.3 规则看不穿的假阳性：等值约束

sprintf((char *)&local_74, "%s.switch", modulename);   // 目标只有 ~48 字节
但进入该分支的前提是：
if ((strcmp(modulename, "accountfilter") == 0 ||
     strcmp(modulename, "qosrule") == 0) && ...)
长度已被 strcmp 钉死在 13 字符内 → 不是漏洞。 这类「等值比较即长度约束」的守卫，语句级污点规则看不出来。

5. 这轮暴露的 4 个工具边界

#边界证据修法
1归纳规则绑死在 Tenda httpd 的写法上 换到同机 bin/dhttpd（GoAhead 3.x）：492 函数、24 个有源有汇，却只出 1 条链、保留 0。归纳把 error() / assert() 当成源——源参数是 wp->putname && wp->filename、0 <= size && size < bp->buflen 这种断言表达式；真正的 websGetVar 反而没识别 源归纳加「参数是否像变量名 / 是否像断言」判别；补 GoAhead 档案
2等值约束看不穿§4.3把 strcmp(x,"literal")==0 作为长度上界写进守卫模型
3调试日志被当格式化字符串2 条 fmt 链全是 printf(常量格式, 用户实参)，且包在 cgi_debug=="on" 里fmt 判定要求首参被污染，否则不算
4缺端点可达性判定§4.2 的死代码会污染结果把 M2 的 route→handler 反查进 M3 verdict：未注册且无 xref → unreachable

6. 为什么这个负结果是可信的

  • NVD 中可检索到 106 条与 Tenda AC15 相关的 CVE，其中大量直接写死 V15.03.05.19，时间跨度 2018–2026。
  • 同源代码复用在 AC6 / AC9 / AC10 / AC18 / AX3 / AX1806 / AC21 / AC23 上：任何一个函数被谁报过，基本都会覆盖到这里。
  • 工具报出的 24 个可达函数，用函数名 + 路由名双路检索后全部有主；唯一没有主的，用交叉引用证明为不可达。
  • 因此结论不是「工具没找到」，而是「这个攻击面已经被 fuzz 饱和」——工具在这里只能高效复现。
负结果的边界：本轮只覆盖了 bin/httpd 一个二进制、以及 M3 实际分析到的 783 个函数。 同一固件里 minidlna、dhttpd、app_data_center 未展开， 不能据此宣称「整个固件没有零日」。
