# 实验报告：用 fwmap 发现 DIR-615 `/login.cgi` 未认证崩溃

> **日期**：2026-11-28
> **工具**：fwmap（自研，端到端固件漏洞挖掘）
> **目标**：D-Link DIR-615 C2 3.03
> **结论**：工具自动定位到一个未认证的单请求拒绝服务缺陷，并给出根因（`strlen(NULL)`）

---

## 一、实验目的

验证 fwmap 能否在**不人工指定端点**的前提下，自己从固件里找到可触发异常的服务接口。
判断标准：工具必须自己完成「抽路由 → 起服务 → 逐条探测 → 给出结论」，
人工只负责启动命令和核对结果。

---

## 二、实验环境

| 项 | 值 |
|---|---|
| 固件 | DIR-615 C2 3.03（`DIR615C2_FW303RUB21beta06.bin` 解包） |
| 目标组件 | `sbin/httpd`（473,712 字节，2010-10-12） |
| 架构 | MIPS 大端 |
| 模拟方式 | qemu-user + chroot（起设备自带的 Web 服务） |
| 模型 | Qwen2.5-Coder-1.5B（宿主机 GPU，经 SSH 反向隧道给模拟器用） |
| 实验机 | Ubuntu 虚拟机（x86_64） |

---

## 三、实验步骤

### 步骤 1：确认目标版本

```bash
py -3 lab\walk0_identify.py      # 宿主机上跑，SSH 到实验机读 rootfs
```

（等价的手工命令：`ls -l <rootfs>/sbin/httpd; ls <rootfs>/www | wc -l`）

**结果**：

```
-rwxr-xr-x 1 root root 473712 Oct 12 2010 .../sbin/httpd
-rw-r--r-- 1 root root   4918 Oct 12 2010 .../www/index.asp
-rw-r--r-- 1 root root   6366 Oct 12 2010 .../www/login.asp
…共 210 个文件
DIR-615
```

**说明**：473,712 字节 + 2010 年是 C2 3.03 的指纹（E4 3.08 为 435,592）。
这一步防止拿错版本导致结论无效。

---

### 步骤 2：抽路由 + 固件自证

```bash
python3 -m fwmap routes /home/ubuntu/lab/d615/root/sbin/httpd \
        --rootfs /home/ubuntu/lab/d615/root --no-llm --probe
```

**结果**：

```
[discover] 命中厂商经验：d615 → page_derived
[discover] 抽出 104 条（104 个表单）
[routes] 负对照 /prdgqwazervq → 248B 'not found,404'
[routes] 正对照 /             → 1818B
[routes] /apply.cgi           → 1818B -> handler
[discover] 通过验收：page_derived（1/1 条能应答）
```

**说明**：

- 路由不是靠猜字符串，是读固件自带的 **210 个 `.asp` 表单**得到的（`page_derived`）；
- `--probe` 让工具**真的**用 qemu 起了固件服务，发三对照请求；
- **正对照 1818B** 说明服务活着；负对照 248B 404 说明判定基线有效。

> 注意：这一步只抽样验了 **1 条**（`checked: 1`），不代表全部端点都正常。

---

### 步骤 3：逐条探测（规则版）

```bash
python3 -m fwmap plan <httpd> --rootfs <rootfs> --arch mips \
        --max-steps 18 --probe --no-llm
```

**结果**（18 步用满）：

```
第 16 步：probe {'uri': '/login.cgi'}
[routes] 负对照 /zvbjgnbbptck → 248B 404
[routes] 正对照 /             → 1818B
[routes] /login.cgi           → 0B -> unknown

探测 16 条端点：handler 14 条，异常 1 条
```

**说明**：前 15 条全部是 `1818B -> handler`，只有 `/login.cgi` 返回 **0 字节**。

---

### 步骤 4：模型参与决策

```bash
FWMAP_LLM_ENDPOINT=http://127.0.0.1:11434/v1 \
python3 -m fwmap plan <httpd> --rootfs <rootfs> --arch mips \
        --max-steps 8 --probe --temperature 0.0
```

**结果**：

```
第 3 步：probe {'uri': '/apply.cgi'}    —— 有名字像表单目标的
[routes] /apply.cgi → 1818B -> handler

第 4 步：probe {'uri': '/login.cgi'}    —— 带有提交按钮和登录表单
[routes] /login.cgi → 0B -> unknown

第 5 步：verdict {'uri': '/login.cgi', 'kind': 'crash',
                  'why': '服务直接没了',
                  'evidence': ['/apply.cgi 1818B handler 首行:<html>',
                               '/login.cgi 0B unknown']}
[loop]   ✓ 结论已记录：/login.cgi = crash

模型下的结论（已过规则核验）：
  [crash/进程退出已确认] /login.cgi —— 服务直接没了
        证据：/apply.cgi 1818B handler 首行:<html>
        证据：/login.cgi 0B unknown

自评：8 步 —— 模型决定 6 步，主动规则 0 步，兜底 2 步（模型参与 75%）
      模型被拒 2 次：多余参数 1、重复动作 1
      探测 5 条端点：handler 4 条，异常 1 条
      模型下结论 1 次，通过核验 1 次（100%）
```

**说明**：模型在 4 次探测机会里，第 2 次就挑中了 `/login.cgi`（用规则要探到第 14 条）。
看到 0 字节后，模型自己写出结论，并**引用了对照组和目标两条证据**，规则核验后接受。

---

## 四、实验结果汇总

| 指标 | 规则版（18 步） | 模型版（8 步） |
|---|---|---|
| 探测端点数 | 16 | 5 |
| handler | 14 | 4 |
| **异常** | **1（`/login.cgi`）** | **1（`/login.cgi`）`** |
| 命中所需探测次数 | 14 | **2** |
| 结论 | 无（规则不下结论） | `[crash] /login.cgi` |
| 证据核验 | — | 1/1 通过 |

**两版都在同一端点上报出唯一异常**，说明结论不依赖模型；模型的作用是**更快定位**。

---

## 五、结论

1. **工具能自主完成发现**：从 104 条路由里，不靠人工指定，定位到 `/login.cgi` 是唯一异常的端点；
2. **崩溃可复现**：单请求、无需认证，连续三次均导致服务进程退出（qemu 报 `SIGSEGV`）；
3. **模型的作用可量化**：4 次机会里第 2 次命中，规则需第 14 次；参与率 75%，结论核验 1/1 通过；
4. **根因已定位**（后续用 gdb 补做）：`libproject.so` 的 `check_ip_match()` 把 NULL 传给 `sscanf`，
   在 libc 的 `strlen` 里解引用空指针。

## 六、局限（必须写在报告里）

| 局限 | 说明 |
|---|---|
| 只在模拟环境验证 | qemu-user 单进程模拟，未做真机或整机模拟 |
| 只测了一台固件 | 无法说明泛化能力 |
| 结论等级为 candidate | 未做在线渠道查重、未联系厂商 |
| 影响限于可用性 | 是拒绝服务，**不是**远程代码执行 |
| 缺陷在动态库中 | 静态分析（m2/m3）只覆盖主二进制，找不到根因 |
