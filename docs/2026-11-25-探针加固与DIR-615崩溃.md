# 2026-11-25：探针加固、DIR-615 崩溃候选、以及一次真实的 fork 炸弹

## 一、DIR-615 的 `/login.cgi` 崩溃（新的候选）

### 现象

```
GET /login.cgi                    → 0 字节，httpd 进程被 SIGSEGV 打死
GET /login.cgi?graph_id=1         → 1818 字节，200 Ok，服务存活
GET /login.asp                    → 3258 字节，200 Ok
POST /login.cgi（无 graph_id）     → 0 字节，进程崩溃
```

### 复现数据（每次重新起服务）

| 次数 | 请求 | 字节 | 状态 | 服务存活 |
|---|---|---|---|---|
| 1 | GET /login.cgi | 0 | no-crash | 是 |
| 2 | GET /login.cgi | 0 | **crash** | **否** |
| 3 | GET /login.cgi | 0 | **crash** | **否** |
| 4 | GET /login.cgi?graph_id=1 | 1818 | no-crash | 是 |
| 5 | GET /login.cgi?graph_id=1 | 1818 | no-crash | 是 |

**与输入相关**：带 `graph_id` 就不崩 → 不是环境缺失导致的假崩溃（对照组的教训用上了）。
一个**未认证的 GET 请求即可让 Web 服务退出**，属于可用性影响（DoS）。

### 查重

| 查询 | 命中 | 说明 |
|---|---|---|
| `DIR-615 login.cgi` | CVE-2017-9542 | 是**认证绕过**（modified POST），不是崩溃 |
| `DIR-615 graph_id` | 0 条 | 没有相关记录 |
| `DIR-615 denial of service` | CVE-2017-7404 | CSRF 类，与本题无关 |

**结论：目前未发现覆盖「未带 graph_id 导致 login.cgi 崩溃」的公开记录**，
可作为"未报告目标上的候选"；但它只是 DoS，写论文时按 DoS 定位，不要夸大成 RCE。

## 三、一次真实的 fork 炸弹（工具安全问题）

### 发生经过

测 Edimax 的 `bin/webs`（Boa）时，之前误把 `usr/sbin/httpd`（busybox 符号链接）
当服务启动，并用 `-h /web -p 80` 请求页面。结果 busybox httpd 把自己当 CGI 再执行，
形成链式自我复制：

```
busybox httpd → fork → busybox(作为CGI) → fork → busybox → ...
```

**虚拟机上滚到 508 个 busybox 进程、load average 513**，SSH 一度不可用。

### 根因

不是固件的问题，是**"在宿主机上直接跑不可信程序"的必然风险**。
以前只按单个请求超时控制，没有限制进程数。

### 修复

`fwmap/dyn.py` 增加资源围栏：

```python
def _child_limits():
    resource.setrlimit(resource.RLIMIT_NPROC, (64, 64))   # 最多 64 个进程
    resource.setrlimit(resource.RLIMIT_CPU, (120, 120))   # 最多 120 秒 CPU
```

所有服务启动（`run_request` 与 `ServiceSession`）统一走 `_popen_kwargs()`，
子进程继承这两个上限。

### 验证

同一台固件、同一个 busybox httpd、连打 6 次请求：

```
起始 busybox 进程: 0
  第1次  183B → 1
  第2次  183B → 1
  第3次 4096B → 1
  ...
停止后: 0
```

**进程数被钉死在 1，宿主机安全了。**

## 六、登录/口令：新接一类工具（auth）

### 6.1 为什么接这一类

post-auth 的链（`apply.cgi` 的 sprintf、`ping_response.cgi` 的溢出）都卡在"要登录"。
所以给工具总线补一个 `auth` 能力，让模型在有登录页的固件上能选它。

### 6.2 接了什么

| 工具 | 类型 | 说明 |
|---|---|---|
| `default-creds` | 内置 Python | 按常见默认口令表试登录；**成功判据是拿到会话 Cookie 或管理页特征** |
| `hydra` | 外部 | 经典 HTTP 表单爆破（需人工给表单参数与成功串） |
| `routersploit` | 外部 | IoT 专用框架，自带厂商默认口令与利用模块 |

外部两个只登记了入口（`--help` 级），要真正用起来需要填参数——和 `decrypt` 那批
"厂商脚本挂载点"是一个思路：**总线负责调、验收负责判，脚本质量差就过不了验收。**

### 6.3 成功判据（auth 类最容易自欺）

```python
会话 Cookie（Set-Cookie 且名字像 session/sid/token）  → 成功
管理页特征 >= 3 个（logout/reboot/wireless/wan…）    → 成功
只看到 "login"/"password" 字样                        → 失败
HTTP 200                                               → 不算成功
```

只靠状态码判成功，会把每个登录页都判成"登录成功"。

### 6.4 实测

**假服务**（正确口令返回 `Set-Cookie: session_id`）：

```
admin/(空)   → fail（仍然是登录页）
admin/s3cret → success（拿到会话 Cookie: session_id）
```

**DIR-615 真固件**：

```
admin/(空)   → 空响应
admin/admin  → 连接失败 ConnectionRefusedError
结果: success=False crashed=True
```

**这恰好印证了前面的发现**：DIR-615 的 `POST /login.cgi` 一发就崩，
根本没机会试口令。工具如实报 `crashed`，而不是"口令错误"。

### 6.5 结论

- 对**正常固件**：默认口令探测可用（假服务已验证）；
- 对**有崩溃的登录接口**：爆破无意义，但崩溃本身就是结论——
  这比"试了 N 次没成功"有价值得多。

## 七、Edimax BR-6478AC V2 1.23：默认口令直接进后台

### 7.1 登录形态：HTTP Basic Auth（不是表单）

```
GET /            → 302 Redirect → /index1.asp
GET /index.asp   → 401 Unauthorized
```

`/index.asp` 返回 401 说明用的是 **HTTP Basic 认证**——所以之前按表单找
`login.asp` / `goform/formLogin` 全部 404 是找错了方向。

### 7.2 探测结果（工具自己跑出来的）

```
admin/(空)      → fail（401）
admin/admin     → fail（401）
Admin/(空)      → fail（401）
Admin/admin     → fail（401）
admin/password  → fail（401）
admin/1234      → success（HTTP/1.0 200 OK）   ★
```

**出厂默认口令 `admin:1234` 就能进管理后台。**

这条是 `tools_auth.probe_basic` 在真机上跑出来的，不是手敲的——
说明新接的 `auth` 能力确实能用。

### 7.3 意义

| 项 | 内容 |
|---|---|
| 性质 | 弱默认口令（配置类问题，通常不单独发 CVE） |
| 影响 | 未改口令的设备，任何能访问 Web 的人都是管理员 |
| 与前面结果的关系 | 有它之后，Edimax 的 post-auth 链（CVE-2026-10127 命令注入）就有了入口 |

### 7.4 还差一步

拿到会话后重试 `/goform/formStaDrvSetup` 的注入，**没有打出命令执行**
（响应 184–199 字节，无证据文件）。原因很可能是缺少该处理器要求的其它字段
（页面表单里还有 `stadrv_type`/`stadrv_ssid`/`stadrv_band`/`submit-url` 等）。

下一步应该用 `poc` 模块按 M3 的链数据生成请求，而不是手拼表单。
（之前 exec-confirmed 那次就是用 `poc` 打出来的，说明链路本身通。）
