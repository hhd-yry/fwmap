# dyn 的验证边界（2026-11-25 结论）

> 一句话：**工具的"请求内容"是对的，"状态判定"在 fork 型服务上不可靠。**

## 一、已经验证成立的部分

| 能力 | 证据 |
|---|---|
| 认证（Basic） | Edimax `admin:1234`，工具探测出来，请求带认证成功 |
| 字段补全 | 从页面抽 18–19 个字段（`param_llm`） |
| 载荷构造 | `00:11:22:33:44:55'$(cmd)'`，从 M3 的 guard 推导 |
| **实际执行** | 同一份 421B body 单独发送 → `1523B` + 证据文件 `FWMAP-TOOL-CONFIRMED` |

**"工具给出料 → 打出去 → 命令执行"这条路是通的**，只不过最后一发是在脚本里发的。

## 二、不可靠的部分：dyn 的状态判定

| 场景 | 现象 | 原因 |
|---|---|---|
| Edimax（Boa，fork CGI） | 重打那一发 0 字节，无执行 | 服务端关连接；重启/换进程/换会话均无效 |
| DIR-615（httpd，fork 子进程） | `POST /login.cgi` 直接发会 `crash`，dyn 却报 `no-crash` | 父进程要等子进程退出后才死，判活太早 |

两件事的共同点：**dyn 假设"一个请求对应一个进程的生命周期"，而固件服务普遍是 fork 模型。**

## 三、已经修掉的（每一处都会让"打不中"伪装成"没漏洞"）

1. `--port` 默认 8080，而 Boa 只认配置里的 80 → 全部 `no-listener`
2. Boa 守护化（父进程 exit 0）被当成启动失败
3. 端口 TIME_WAIT → 后续 bind 失败
4. 三个页面字段混发（110 个）→ 处理器拒绝
5. 模板值 `<% getInfo %>` 塞进表单
6. MAC 类参数没有 MAC 前缀 → 到不了拼接点
7. 0 字节响应时判活太早 → 补一次"再看一眼"

## 四、下一步（要么修判定，要么绕开）

| 方案 | 做法 | 成本 |
|---|---|---|
| A | 用 `fork` 感知的判定：请求后轮询端口 + 进程树（含子进程）状态 | 半天 |
| B | 每发请求用**独立 chroot 副本**，请求后检查进程表里是否还有该二进制 | 半天 |
| C | 放弃"自动判定"，工具只出料（字段/载荷/认证），执行交给小脚本 | 0 |

**当前建议 C（论文可用）**：论文里把 dyn 定位成"PoC 生成器 + 可选的自动验证"，
自动验证的可靠性列为"已知限制"，比硬吹"全自动"更稳。

## 五、给论文的说法

> 本系统的动态验证模块能够生成可直接执行的验证请求（含认证、完整字段与
> 针对处理器拼接方式定制的载荷），并在服务进程模型简单的目标上自动判定结果；
> 对于采用 fork 模型的服务，进程生命周期与请求不再一一对应，自动判定存在
> 时序误差，因此提供"生成 + 人工/脚本执行"的降级路径。
