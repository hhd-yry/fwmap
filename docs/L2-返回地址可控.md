# L2：把「崩了」变成「返回地址可控」

> 目标：`bof` 类的链不再止于「打崩了」，而是给出**偏移**和**可控证据**——
> 「载荷第 132 字节起覆盖 `$ra`」这种话，才是能写进报告的可利用性结论。

## 1. 做法

```
cyclic pattern（de Bruijn，任意 4 字节唯一）
   → 作为参数打进目标
   → qemu -g 起服务，gdb-multiarch 连上去 continue
   → 目标崩 → gdb 停在 SIGSEGV → info registers 拿到 pc/ra/sp
   → 在 pattern 里反查这两个值 → 偏移
```

命令：

```bash
fwmap bof out/3_m3.flow.json --m2 out/2_m2.json \
    --binary out/root/bin/webs --rootfs out/root \
    --port 80 --only formStaDrvSetup \
    --lengths 64,200,512,896,1024,1536 -o bof.md
```

## 2. 已经解决的三个坑

| 坑 | 现象 | 解法 |
|---|---|---|
| gdb 不知道目标架构 | `Truncated register 39 in remote 'g' packet`，寄存器全 0 | `set architecture mips` + `set endian little` |
| SSH 非交互会话里 gdb 连 socket 被打断 | `:12345: Interrupted system call` | 用 `script -qec` 套一层 pty |
| binfmt 无法带 `-g` | 内核替我们 exec 解释器，加不了参数 | 把静态 `qemu-<arch>-static` 拷进 rootfs，`chroot` 里直接跑它 |

## 3. 当前卡点：目标是 fork 型的

Boa 每来一个连接就 fork 一个子进程处理，**崩溃发生在子进程**。
qemu 的 gdbstub 只盯着主进程，`set follow-fork-mode child` 也不生效，
于是 gdb 看到的是：

```
0x3ffbba80 in ?? ()
[Inferior 1 (process 1) exited normally]     ← 父进程正常退出
```

也就是说：请求发了、服务处理了，但我们看的是「爸爸」，出事的是「儿子」。

### 三条可行出路（按推荐度）

1. **读 qemu 的 core dump**。崩溃时 qemu 会打印 `dumping core in /tmp`，
   ELF core 的 `PRSTATUS` note 里就有崩溃瞬间的寄存器。这条路不依赖 gdb，
   也不受 fork 影响（qemu 自己写的是子进程的 core）。
2. **attach 子进程**。gdb 连上后 `continue`，另起一个线程轮询 `/proc/<pid>/task`
   找新 fork 出的子进程，`attach <pid>` 再 `continue`。
3. **让目标不 fork**。部分 Boa 编译带 `-n`（no fork）或配置项；这个固件没有。

## 4. 结果：gdb 这条路被 fork 挡住，改用二分阈值

`follow-fork-mode child` 对 qemu-user 的 gdbstub 无效，core dump 也没落地，
所以换了个**不依赖 gdb** 的可观测量：**最小崩溃长度**。

```bash
fwmap bof out/3_m3.flow.json --m2 out/2_m2.json \
    --binary out/root/bin/webs --rootfs out/root \
    --port 80 --only formStaDrvSetup --threshold --hi 4096
```

实测（Edimax BR-6478AC，`formStaDrvSetup` 的 `rootMac`）：

```
二分区间 [32, 4096] …
      2064 → 崩      1048 → 崩      540 → 不崩
       794 → 不崩     921 → 崩       857 → 崩
       825 → 崩       809 → 崩       801 → 崩
       797 → 不崩
[+] 最小崩溃长度 ≈ 801 字节（797~801 之间）
```

**参数超过约 800 字节就盖到栈帧控制流上。** 这个数字和静态分析对得上：
反编译里 `sprintf` 的目标缓冲区是 `acStack_340`（`0x340` = 832 字节的帧内偏移），
800 字节左右正好越过帧内缓冲区。

## 5. 这个数字是什么、不是什么

| 是 | 不是 |
|---|---|
| 真实测出来的阈值（二分，4 字节精度） | 精确的 `ra` 偏移 |
| 说明「多长就崩」，可直接判断触发难度 | 证明 PC 可控 |
| 和静态帧布局互相印证 | 能直接拿去做 exploit 的偏移 |

中间可能还隔着几个保存寄存器（`s0`-`s7`），所以真正的 `ra` 位置 ≥ 801。
要拿到精确值，还得解决 fork 取证问题（见下）。

## 6. 还没解决：fork 型目标的崩溃取证

Boa 每连接 fork，崩溃在子进程；qemu 的 gdbstub 只盯主进程，`follow-fork-mode
child` 无效，core dump 也没落盘。三条可选路线：

1. 读 qemu 的 core dump（`qemu_<bin>_<ts>_<pid>.core`）—— 需要让 qemu 真的写出来；
2. 轮询 `/proc` 找到新 fork 的子进程并 `attach`；
3. 换一个不 fork 的目标（比如 `axhttpd`）先用同一条链路验证。

**工具不会假装有结论**：拿不到偏移就输出「没拿到可控证据」，
不会把「父进程正常退出」说成「不可利用」。
