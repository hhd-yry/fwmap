### ✅ probe 接进 agent 循环：让模型自己挑端点（任务 4）

之前 `probe` 在动作白名单里但没接上，`_execute` 里探针恒为 `None`，模型选了也只会
得到一句「没有可用的固件探针」。这次把三件事接起来：候选端点进状态（`candidates`
+ 参数）、模型挑的 uri 原样送进固件、固件裁决（handler / not-found）回填 `probed`。

**第一次跑就撞上一个真问题**：1.5B 在「自由选动作」下选不动 —— 连跑 6 步一次都没
选过 probe，四条 probe 全被规则兜底成固定顺序。trace 里看着像模型挑的，实际全是
`_heuristic` 发的。这会把规则的功劳算到模型头上，比跑不动更危险。

于是加了两处：`source` 字段（model / heuristic，谁做的决定可分辨）和**受限决策** ——
阶段由规则收束，端点由模型挑。收窄成「这 N 条里挑哪一条」之后，1.5B 答得出来。

#### 实验（DIR-615 C2 3.03，同一固件、同一预算：6 步 / 4 次 probe）

| | 固定顺序（`--no-llm`） | 模型自挑 |
|---|---|---|
| probe 1 | /apply.cgi ✓ | /apply.cgi ✓ |
| probe 2 | /online_firmware_check.cgi ✓ | **/login.cgi → 0 B（unknown）** |
| probe 3 | /log_first_page.cgi ✓ | /save_log.cgi ✓ |
| probe 4 | /log_last_page.cgi ✓ | /online_firmware_check.cgi ✓ |
| handler 命中 | **4 / 4** | 3 / 4 |

`/login.cgi` 在 36 条候选里排**第 14 位**。

- 固定顺序探 4 条，离它还有 10 条；**模型第 2 条就挑中了**。
- 挑中是带理由的：「带有提交按钮和登录表单」——不是碰巧撞上。
- 那条 0 字节不是探针坏了：三对照里正对照刚返回 1818 B，说明是 `/login.cgi`
  把服务打没了 —— 正是我们那条未认证崩溃。

**诚实的另一面**：固定顺序的 handler 命中率反而更高（4/4 对 3/4），它按抽取顺序
把"活着的页面"扫了一遍，而模型挑的那条把服务打死了。所以结论不是「模型更准」：

> 固定顺序擅长**穷举**，模型擅长**跳着找异常**。
> 前者要探 14 条才轮到 `/login.cgi`，后者 2 条。

### ✅ 让模型自己下结论：verdict 动作 + 证据裁决（晚间）

用户的原话是「感觉工具完全跟 LLM 没啥关系了，不太像一个智能体」。这个判断是对的：
在那之前，模型只做**选择题**（选机制、挑端点），从不下判断，产出的结论全是规则写的。

这次加的是**结论**这一环：

- 新增 `verdict` 动作：模型自己写 `kind`（crash / suspicious / normal）、`why`、
  以及 `evidence`（逐条引用它**实际看到**的实测记录）；
- 探针把「看到了什么」带回来（长度 / 裁决 / 响应首行），不再只回一个 `handler`；
- **规则核证据**：引用的 uri 必须实测过，否则判"像编的"；说 crash 但实测有字节，
  直接驳回。模型可以判断，但不能凭空断言。

**实际跑出来的样子**（DIR-615 C2，8 步）：

```
第 3 步：probe /apply.cgi        → 1818B handler
第 4 步：probe /login.cgi        → 0B unknown（服务没了）
第 5 步：verdict /login.cgi
         kind: crash   why: 服务直接没了
         evidence: /apply.cgi 1818B handler 首行:<html>
         evidence: /login.cgi 0B unknown
```

这条结论是模型写的，证据是它自己探的，规则核对后接受。

**过程中被规则拦下的两次（都值得记）**：

1. 第一次模型把结论下到了 `/apply.cgi` 上，判「normal」—— 避开了真正反常那条。
   规则改成「只能对 0 字节/unknown 的那条下结论」，它就老实了。
2. 更早一次，`verdict` 分支根本没机会触发：一旦进入"挑端点"阶段，`_decide`
   就只问挑哪条，模型被锁死在 probe 循环里，8 步全探完也没下结论。

**还差什么**：现在模型只在"下结论"和"挑端点"两个窄问题上做主，
流程骨架仍是规则定的。这离"自主挖漏洞"还有距离，但至少不再是"流水线里解释框"。

### ✅ 自评表：把「错误率高」变成数字（当晚）

之前所有"模型行不行"的判断都靠印象。现在每次跑完自动输出：

```
      探测 5 条端点：handler 4 条，异常 1 条
      模型下结论 1 次，通过核验 1 次（100%）
模型下的结论（已过规则核验）：
  [crash] /login.cgi —— 服务直接没了
        证据：/apply.cgi 1818B handler 首行:<html>
        证据：/login.cgi 0B unknown
```

四个数各自回答一个问题：

| 数 | 回答什么 |
|---|---|
| 模型参与率 75% | 模型是不是真的在驱动流程（还是又被流程锁死了） |
| 被拒 2 次 / 原因分布 | 是模型不听话，还是我的校验在瞎拦 |

**今天这条链完整了**：模型挑端点 → 看到 0 字节 → 自己下结论 → 引用证据 → 规则通过。
从"流水线里解释别人的结果"变成"自己看、自己挑、自己判"。

#### ⚠️ 但这 5 次一致不能当"稳定"的证据

`llm.chat()` 默认 `temperature=0.0`，是贪心解码 —— **同样的输入必然同样的输出**。
所以这 5 次证明的是**可复现**（换个时间、换台机器、照着文档跑，结果一样），
**不是鲁棒性**（换个说法、换个固件、让模型自由发挥，还能不能行）。

要测鲁棒性得改三样里的至少一样：温度（>0 采样）、固件（换型号）、提示措辞。
这条必须写进论文的"实验局限"，否则 5/5 会被当成过度拟合的证据。
