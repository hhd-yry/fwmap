# fwbench：fwmap 的端到端交互能力评测器（综述与首轮结果）

> **日期**：2026-11-28　**版本**：fwbench 0.1.0
> **被测系统**：fwmap（自研固件漏洞挖掘工具）
> **文档用途**：交给外部评审，请判断评测设计是否站得住
> **一句话**：这是一个**能跑、能复算、能抓实现缺陷**的评测器，但**当前用例区分不出策略**。

---

## 一、它要回答的三个问题

1. **模块能力**：fwmap 的模块能否产出正确结果？
2. **模块组合**：上游产物里的证据，能否传到最终给用户看的报告里？
3. **模型参与**：条件相同，允许大模型参与决策，哪些任务更好、哪些更差、代价多少？

"端到端"在本项目里的定义：**领任务 → 选只读工具 → 拿反馈 → 提交有证据的结论
（或说明无法判断）**。评分只看最终提交与它引用的证据，不看中间思路。

---

## 二、分层：内核不认识被测工具

```
fwbench/                    ← 通用内核（零 fwmap 依赖）
  cases.py      用例加载、校验、公开视图
  adapters.py   策略（rule / scripted）与回放后端
  runner.py     执行、预算、断点续跑、被测工具调用
  events.py     按步事件、归一化、旧字段兼容
  scoring.py    独立评分（不调模型、不读运行器内存）
  report.py     Markdown 与机器可读汇总（同源渲染）
  archive.py    历史归档复算
  subjects/     被测工具适配器（唯一与具体工具打交道的地方）
    fwmap_elf.py       fwmap.elf.read_elf
    stdlib_elf.py      纯标准库参考实现
    elftools_elf.py    可选依赖 pyelftools
    fwmap_agent.py     调 fwmap 生产决策 loop._decide
bench/                      ← 任务包（用例 / 夹具 / 金标 / 配置 / 归档运行）
tests/test_fwbench.py       ← 评测器自身的 39 项检查
```

**已用子进程验证**：把 `sys.modules['fwmap']` 置空后，内核仍可导入并跑 `stdlib` 适配器。
所以"内核与适配器分别导入"不是口号，是可测的。

## 三、四个接口契约

| 接口 | 输入/输出 | 强约束 |
|---|---|---|
| `open_case(case_id, seed)` | 公开任务 + 材料元信息 | 初始视图**不含内容、不含答案** |
| `dispatch(request, ctx)` | 一次只读操作 → 结果/证据 id/结构化内容 | 回放后端必须**按请求**取材料，不能不看请求发预制答案 |
| `run_subject(...)` | 驱动被测工具 → 原始提交、停止原因、事件流 | 保存实际调用的入口、版本、决策来源；只跑替身要标 `harness-only` |
| `score(run_artifacts, oracle)` | 从已落盘提交与可见证据算通过标志 | **不调模型、不读未来事件** |

---

## 四、防作弊的三条硬规矩

1. **金标只在评分阶段加载**，运行器全程看不到（测试断言：运行目录里没有 oracle 文件）；
2. **公开 ID 与文件名不编码答案**（`case_id` 含 `exit/running` 等词会被 `validate` 直接拒）；
3. **配对两例只差一条记录**，且必须同家族、同 `pair_id`、同集合（dev 与 holdout 不混）。

---

## 五、评分口径

一条提交要同时满足四条：

| # | 条件 | 失败码 |
|---|---|---|
| 1 | `outcome=answered`（或金标允许弃权） | `abstain_not_allowed` |
| 2 | `claim` 与 `expected` 完全一致 | `claim_mismatch` |
| 3 | 每条引用**本轮都读过** | `citation_not_read` |
| 4 | 引用**支持该主张**（主体、采样时间一致，且有 `state` 时与主张一致）并命中一组"充分证据" | `citation_unsupported` / `insufficient_evidence` |

失败只记**第一处**能解释失败的原因。指标：

- 有证据任务通过率（主）：通过数 / **适用**用例数
- 双例通过率：一对两例都过才算 1
- 无依据的确定结论率：有结论但依据缺失/冲突/指向错对象的轮次 / 有结论的轮次
- 未运行（`not_run`）：被测工具不可用 → **不计入分母**，不是 0%

## 六、四个策略

| 组 | 实现 | 用途 |
|---|---|---|
| **H** 基线 | `policy=rule`：跳过纯日志、按记录类型选材料、主体匹配即作答（开发集上写一次即冻结） | 检验"模型收益有多少能被领域知识解释" |
| **S** 脚本 | `policy=scripted`：固定序列 | 只验证管线，**不代表任何能力** |
| **M** 模型 | `--subject fwmap-agent`：调 fwmap 生产决策 `loop._decide`，模型提议、规则兜底 | 主对照的另一半 |
| A 层对照 | `--subject fwmap / stdlib / elftools` | 同一批用例换被测工具 |

每步事件记录三个归属字段：`proposed_by`（谁提议）、`executed_by_policy`
（最终采用谁的）、`fallback_reason`（为什么没采纳）。旧记录缺字段写 `unknown`，不猜。

## 七、做了什么（P0→P4）

| 阶段 | 交付 | 关键判据 |
|---|---|---|
| P0 | 生产入口调用图、覆盖矩阵、字段映射、32 例草案 | 每项标明"实调/归档回放/合成" |
| P1 | 垂直切片：运行状态配对双例 + R/S + 事件 + 评分 + 报告 | 答对但引错记录会失败；重评分无需执行工具 |
| P2 | 接生产决策入口（`fwmap-agent`）+ 归档回归 #1–#4 + `--resume` | 归档三组 5/5、5/5、0/5 可复算 |
| 第9节 | 内核/适配器分离 + 跨工具（3 个 subject） | 无 fwmap 环境仍能跑第二工具 |
| P3 | 真实模型、冻结 H、dev(3对)/holdout(2对)、逐步归属 | M 组能记录提议/兜底/成本 |
| P4 | 首轮验收：覆盖矩阵、成本、失败分析、重算说明 | 另一位读者可从产物重算 |

## 九、评测器抓到的真失败

| 用例 | 现象 | 处理 |
|---|---|---|
| `c203` 截断 ELF | `fwmap` 报 `not_elf`，`stdlib` 报 `truncated` | 判定 fwmap 分类有误 → 修 `elf.py`（分开判魔数与长度）→ 两边都 3/3 |

**这是这一轮唯一被独立金标抓出来的实现缺陷**，也是"评测器有用"的直接证据。

## 十、最关键的一条判断

> **实现区分度 ≠ 0，策略区分度 = 0。**

H、S、M 在开发集上**都是 100%**。也就是说：现有 5 个家族的用例，任何"按类型读一条
权威记录"的做法都能答对，**无法区分模型与规则**。

要测出模型价值，必须构造**规则会挑错、而模型能从内容判断**的用例
（例如：权威记录与任务主体**部分**匹配，或干扰项与目标同名不同版本）。

## 十一、自评：这套评测设计的弱点

1. **任务太容易**：如第十节，区分度为 0；
2. **样本小**：dev 3 对、holdout 2 对，只够描述性比较，不能推断总体；
3. **家族不全**：计划 6 个家族，只实现 5 个（"报告一致性"未做）；
4. **B 层空缺**：模块组合（上游产物 → 报告）一例都没接；
5. **M 组只跑了一对**：模型每步约 20 秒，全量需 20+ 分钟，本轮未跑；
6. **金标全部 provisional**：没有第二人依据原始材料复核（计划第 7 节 #5）；
7. **没有新旧版本回归**：机制（manifest 固定 + `flips`）就位，但还没有第二个可安装版本；
8. **`elftools` 未真跑**：只验证了"缺依赖 → 不适用"这条路径。

## 十二、想请评审回答的问题

1. **用例设计**：要区分"模型 vs 规则"，最小的任务改造是什么？我们想到的是
   "主体部分匹配"和"同名不同版本"，是否够？还有别的陷阱值得加吗？
2. **评分口径**：金标用"任一组充分证据"的列表，并要求引用**支持**主张。
   这种设计会不会奖励"刚好引用对"而惩罚"多读了干扰项"？（我们没惩罚多读，只惩罚引用错）
3. **归属**：模型提议被规则接管时，我们把"这一步的成功"算给 M 组系统效果、
   把"这一步选择"算给规则。这个切分是否被审稿人接受？
4. **留出集**：只有 2 对，是否应该干脆不报"留出集结果"，只报 dev？
5. **区分度 = 0 怎么写**：是应当直接写"当前用例无法区分"，
   还是应当先补难度再报告？如果时间不够，哪种写法更诚实也更有说服力？
6. **架构**：内核零依赖 + 适配器 + 任务包的三层切分，是否足以支撑"同一任务包换被测工具"
   这个卖点？还是会被认为过度设计？

## 十三、复现

```bash
# 环境：Python 3.11+；不需要固件/GPU（模型组除外）

python -m fwbench validate --suite bench/suites/dev.json --oracle bench/oracle/dev.json
python -m fwbench archive lab/recordings --expect 5,5,0

# 用仓库自带的运行目录重算（不需要重跑任何工具）
python -m fwbench report bench/runs/2026-11-28/fb-dev-rule --oracle bench/oracle/dev.json
python -m fwbench report bench/runs/2026-11-28/fb-m       --oracle bench/oracle/dev.json
python -m fwbench compare bench/runs/2026-11-28/elf-fwmap \
    bench/runs/2026-11-28/elf-stdlib --oracle bench/oracle/elfmeta.json --out runs/cmp

# 评测器自身的检查（39 项）
python tests/test_fwbench.py
```

**运行产物**：`manifest.json`（版本/条件/摘要）、`cases/*/events.jsonl`（事实来源）、
`cases/*/submission.json`（原始提交）、`results.jsonl`、`summary.json`、`report.md`。
`report.md` 与 `summary.json` 由**同一份汇总对象**渲染，结构上无法不一致。
