# 计划：经验驱动的自适应（L2）

> 状态：**已实现**（2026-11-22），实测结果见文末「十、落地结果」
> 目标版本：v0.9「自适应」 · 预计工时：半天（4 个 1.5 小时块）

## 一、要解决的问题

当前系统已经能记住经验（`knowledge.py`：厂商画像 / 经验卡 / 机制成功率），
但**经验只被"读出"用于跳过探索，没有被"用于排序"**：

```python
# fwmap/discover.py 现状
hinted = preferred(src, names)      # 魔数启发
picked = [n for n in advice if n in names]   # 模型建议
picked = [n for n in hinted if n not in picked] + picked
for t in usable: picked.append(t.name)       # 兜底补齐
```

`stats.json` 里的 `page_derived@dir-816l: ok 3 / fail 0` 这类数据**完全没参与决策**。
后果：面对一台已经证明"`strcmp_chain` 无效"的厂商，系统仍会按模型/魔数的顺序再试一次，
白花一次探测（每次探测要启动一次固件，约 10 秒）。

### 量化目标

同一批固件跑两轮，第二轮满足：

| 指标 | 现在 | 目标 |
|---|---|---|
| 平均尝试机制数 | 未统计 | 下降 ≥ 30% |
| 因历史成功率被提前的机制 | 0 | ≥ 1 次/台 |
| 错误机制被排到最后 | 不保证 | 一定（0 成功率且已试过） |

## 二、范围

### 做

1. 新增 `fwmap/policy.py`：给定「机制 × 厂商」的历史，算出先验分数与排序。
2. `knowledge.py` 增加查询接口（不改变现有 JSON 结构，只加字段）。
3. `discover.choose()` 接入 policy：**模型建议 / 历史成功率 / 魔数启发**三方融合。
4. 连续失败惩罚 + 探索保留（不能让一次坏结果把机制永久封杀）。
5. 开关 `--no-policy`，便于消融实验。
6. 实验与测试。

### 不做

- 不做模型微调（样本量不够，且不可解释）
- 不让系统自己发明新机制（L3，超出本科范围）
- 不改动 `toolbus` 的验收逻辑（那是另一条线，已完成）

## 三、设计

### 3.1 数据结构（在 `stats.json` 每条记录上增字段）

```json
"page_derived@dir-816l": {
  "mechanism": "page_derived", "vendor": "dir-816l",
  "ok": 3, "fail": 0,
  "streak_fail": 0,          // 连续失败次数（成功即清零）
  "last_ok": "2026-11-17 20:12",
  "last_fail": "",
  "updated_at": "..."
}
```

向后兼容：老数据缺字段时按默认值（`streak_fail=0`）处理。

### 3.2 打分

```python
def prior(ok, fail, a=1.0, b=1.0):
    # 拉普拉斯平滑：0 次尝试 = 0.5，1 次成功 = 0.67，1 次失败 = 0.33
    return (ok + a) / (ok + fail + a + b)

def score(mechanism, vendor):
    rec = stats.get(f"{mechanism}@{vendor}") or {}
    base = prior(rec.get("ok", 0), rec.get("fail", 0))
    penalty = 0.5 ** rec.get("streak_fail", 0)   # 连续失败一次减半
    return base * penalty
```

### 3.3 排序（三方融合）

排序键（越靠前越先试）：

```python
key = (
    0 if 未尝试过 and 该厂商有其它机制成功过 else 1,   # 探索优先
    0 if 魔数命中 else 1,                            # 证据优先
    -score(mech, vendor),                           # 历史成功率
    model_rank,                                     # 模型建议
)
```

**为什么把"未尝试"放最前**：探索不能被饿死。若某机制从没在这家厂商试过，
它的分数是 0.5，与"试过一次成功"（0.67）接近，但可能是唯一能成的路。

**模型位置降到最后**：昨天已经证明，模型会固执地选同一条（有回环兜底），
它的价值在"给建议"，不在"决定顺序"。

### 3.4 失败反馈

`discover` 每轮结束调用 `knowledge.bump(...)` 时，
同时维护 `streak_fail`：成功清零，失败 +1。

### 3.5 冷启动

无任何统计时，`score()` 恒为 0.5，排序退化为"魔数 → 模型 → 兜底顺序"，
**与当前行为一致**——保证开启 policy 不会让首次分析变差。

## 五、实验设计（论文用）

**同一批固件跑两轮**（Edimax / DIR-816L / DIR-615）：

| 轮次 | 配置 | 记录 |
|---|---|---|
| A | `--no-policy` | 尝试机制数、总耗时、是否成功 |
| B | 默认（开启 policy） | 同上 + 各机制实际顺序 |

**预期**：B 轮中，历史上失败过的机制被排后，平均尝试次数下降。

**注意**：为保证公平，A、B 两轮都必须**清空 profile 缓存**（保留 stats），
否则 A 会因 profile 命中而虚高。

## 十、落地结果（2026-11-22）

### 10.1 实现了什么

| 文件 | 内容 |
|---|---|
| `fwmap/policy.py` | `prior()` 平滑、`score()` 连败减半、`rank()` 分层排序、`should_override()` 覆盖判据 |
| `fwmap/knowledge.py` | `bump()` 维护 `streak_fail` / `last_ok` / `last_fail` |
| `fwmap/discover.py` | 接入经验排序；模型选错时按经验覆盖；兜底顺序改用 `policy_order` |
| `fwmap/cli.py` | `routes --no-policy`（消融实验用） |
| `tests/test_policy.py` | 22 条测试 |

排序规则（按优先级从高到低）：

```
分层：有成功记录的厂商 → 成功过 > 没试过 > 失败过
     没有成功记录     → 没试过 > 失败过（探索不被饿死）
同层：魔数命中 > 历史得分 > 模型建议
覆盖：候选机制成功过，且分数高出 0.1 以上，才推翻模型的选择
```

### 10.2 实测（Edimax rootfs，模拟固件应答）

```
第 1 轮  模型选 page_derived（对）
         经验排序：page_derived → strings_goform → strcmp_chain
         通过验收 2/3，写库 page_derived@p5: ok=1

第 2 轮  清掉厂商画像、只留成功率；模型选 strcmp_chain（错）
         按历史成功率改用 page_derived（0.67 vs 0.50）—— 原选 strcmp_chain
         第 1 轮就通过验收
```

**效果：尝试机制数 2 → 1，省掉一次无谓探测。**

### 10.3 过程中发现并修掉的 bug（重要）

第一版实现里，`kb.bump(mechanism, vendor, validated)` 直接按 `validated` 落库。
在没有 qemu 的机器上，`validated` 恒为 False，于是"**没跑**"被记成了"**失败**"：

```
page_derived@p5: ok=0 fail=2 streak=2   ← 实际它抽出 188 条路由，只是没条件验收
```

后果是下一轮排序把正确机制压到最后。已修：**只有真正拿到验收结果
（`probe is not None`）才写成功率**，否则只记一条日志"本次没有验收条件"。

这条 bug 本身说明了"经验库必须带验收条件"——记忆写错比不写更糟。

### 10.4 与计划书的差异

| 计划 | 实际 |
|---|---|
| 排序键四元组（探索/魔数/分数/模型） | 改为**分层 + 同层排序**，可读性和可测性更好 |
| 覆盖条件 `top>=0.6 and cur<0.5` | 改为 `ok>0 且分差>=0.1`（margin 规则），避免"没试过=0.5"卡在阈值上 |
| 12 条测试 | 22 条（多出覆盖规则、未验收不写库、连败计数等） |

## 十一、真机 A/B（2026-11-25，VM 上的真实固件）

### 11.1 实验设置

同一台固件，同一份经验，只切换 `--no-policy`：

```
热身：跑一次，让 page_derived 成功，写进 stats
A 组：清掉厂商画像、保留成功率；关 policy；模型故意选 strcmp_chain（错的）
B 组：同样状态；开 policy；模型仍选 strcmp_chain
```

### 11.2 结果

**DIR-615 C2（探针可用，/index.asp 与 /apply.cgi 都能应答）**

| 组 | 模型选择 | 实际尝试 | 最终机制 | 验收 |
|---|---|---|---|---|
| A（关 policy） | strcmp_chain | **2 次** | page_derived | 通过 |
| B（开 policy） | strcmp_chain | **1 次** | page_derived | 通过 |

B 组日志：

```
[discover] 按历史成功率改用 page_derived（0.75 vs 0.50）—— 原选 strcmp_chain
[discover] 第 1 轮：page_derived（置信 0.90）—— 经验优先：page_derived 在这家厂商成功过
[discover] 通过验收：page_derived（1/1 条能应答）
```

**DIR-816L / Edimax(root2)**：探针能起，但所有机制都验不过（index.cgi 依赖 somovd；
root2 的 webs 不认这些路由），没有成功历史 → 经验排序**不改变行为**（3 次 vs 3 次）。
这符合设计：**没有成功经验时，policy 不应该乱改顺序。**

### 11.3 实验过程中修掉的两个真 bug（比 A/B 本身更重要）

**bug 1：探测请求用了 POST。**
`routes._req()` 默认构造 `POST path + body x=1`。DIR-615 的 httpd 对静态 `.asp`
的 POST 直接关连接（0 字节），于是 `/index.asp` 被判成 `unknown`，
整个路由验收全线失败。改成默认 **GET** 后：

```
负对照 /sihrjeofeprq  → 248B 'not found,404'
正对照 /              → 1818B
/index.asp            → 1818B -> handler   ✅
/apply.cgi            → 1818B -> handler   ✅
```

**bug 2：每个请求都重启一次服务。**
`routes.probe` 逐地址调用 `run_request`，每次起一次 chroot 服务再杀掉。
DIR-615 上 3 次里有 2 次拿到 0 字节——上一轮的 chroot 进程还没退干净，下一轮 bind 失败。
新增 `dyn.ServiceSession`（一次启动、多次请求、按需重启），探针改用它之后
连打 9 次请求全部 200，且总耗时从「N 次 × 3–8 秒」降到「1 次启动 + N 次请求」。

**这两个 bug 的存在说明**：在真机上，"机制选择"之前还有一层更基础的问题——
**探针本身能不能正确地问固件**。之前所有"路由验收失败"的结论都值得重新跑一遍。

### 11.4 结论

- 经验排序在**有成功历史**的固件上有效：尝试机制数 2 → 1，省掉一次无谓探测；
- 在**没有成功历史**的固件上不改变行为（符合设计，不乱动）；
- 真机数据目前只有 1 台（DIR-615），样本量不足以下统计结论，
  但已能证明机制可用、且修掉了两个会污染所有路由结论的 bug。

### 12.2 最重要的一条：DIR-816L 的旧结论是错的

之前的记录写的是「DIR-816L 的页面全部返回 unknown，因为依赖 somovd」。
用修好的探针重跑：

```
[routes] /index.cgi   4096B -> handler
[discover] 通过验收：page_derived（1/2 条能应答）
路由：5 条
```

**原因不是 somovd，而是探测请求用了 POST**：`index.cgi` 对 POST 直接关连接，
对 GET 正常返回 4096 字节。改 GET 之后路由立刻可达。

> 教训：当一整类固件"全部不可达"时，先怀疑探针，再怀疑固件。

### 12.3 仍然到不了的三台

ASUS / TEW-818 的 `usr/sbin/httpd` 是怎么都起不来的（试了 7 组启动参数，
全部 no-listen）；Edimax root2 能监听但不回应请求。三者的共同点是**都要读 NVRAM**：
固件里 `/dev/nvram` 在我们的 chroot 里不存在，服务初始化到一半就退。

这类只能靠全系统模拟（`fwmap emulate`）解决——目前只做了启动器，
profile 还没填，这是已知的研究边界。

## 十三、NVRAM 复活尝试（2026-11-25，结论：user-mode 下做不到）

目标：把起不来的 ASUS / TEW-818 / Edimax 救活。结果逐个说：

### 13.1 ASUS / TEW-818：卡在 NVRAM，不是缺设备

```
$ chroot tew818_root /usr/sbin/httpd
httpd:No LAN IP address and protocol specified.
/usr/sbin/httpd:can't bind to any address
```

试过 7 组启动参数（`-p`/`-h`/`-c`/裸跑/传 IP），输出完全一致 —— 说明它不看命令行，
而是从 NVRAM 读 `lan_ipaddr` / `lan_proto`。固件里 `libnvram.so` 导出
`nvram_get/nvram_getall/nvram_set`，`/dev/nvram` 是个 64 KB 普通文件。

试过用固件自带的 `nvram` 工具写入：

```
$ chroot tew818_root /bin/sh -c 'nvram set lan_ipaddr=192.168.1.1; nvram get lan_ipaddr'
（无输出，rc=0）
```

**写入无效** —— 该工具是 4 KB 的桩，`/dev/nvram` 也按文件读不出结构。
要真正喂 NVRAM，需要给 ARM/MIPS 交叉编一个 `LD_PRELOAD` 垫片拦截
`nvram_get`，或者上全系统模拟。**本次不做，记为研究边界。**

### 13.2 Edimax root2：服务器能跑，但路由是错的

之前选错了服务二进制（`usr/sbin/httpd` 其实是 busybox 的符号链接）。
改用真正的 `bin/webs`（Boa 0.94）：

```
boa: starting server pid=56833, port 80
/             → 302 Redirect
/aconnected.asp → 200 OK（3985 B）
/goform/chkLink → 404 Not Found
```

用这个可用的正对照重新探测 page_derived 抽出的 188 条 `/goform/*`：

```
负对照 /rxbyzqbdvlqi  1035B 'not found,404'
正对照 /aconnected.asp 3985B
/goform/chkLink       1035B -> not-found
/goform/formPasswordSetup 1035B -> not-found
```

**结论：这颗固件的网页里写的 `/goform/*` 在这版固件上根本不存在**（404）。
这不是探针的问题，而是「页面里写的接口 ≠ 固件真的实现了」——
**路由自证机制正好把这类"看起来对、其实不存在"的候选挡掉了。**

### 13.4 顺带加的两个能力

1. `routes.probe(positive_path=...)` / `firmware_probe(positive_path=...)`：
   正对照路径可配置——Edimax 的 busybox httpd 对 `/` 会挂住不返回，
   但 `/aconnected.asp` 正常，没有这个参数就永远拿不到正对照。
2. 服务二进制选择要避开 busybox 符号链接：`usr/sbin/httpd → ../../bin/busybox`
   是静态服务器，不处理 `/goform/*`；真正的服务是 `bin/webs`。
