## 四、模型带来的最大正负变化

| 变化 | 用例 | 数据 |
|---|---|---|
| 正向 | — | **没有观察到**：没有一例是"规则错、模型对" |
| 负向（成本） | `c017`/`c018` | 模型 3 次工具调用 vs 规则 1 次；且第一步读了干扰记录 `e3` |
| 负向（兜底） | `c017` | 最后一步模型提议 `pages` 被重复守卫拒绝，由规则输出 `done` |

**这不是"模型没用"的证明**，是"**当前用例太容易**"的证明。要测出模型价值，需要
规则会挑错、而模型能从内容判断的用例（例如权威记录与任务主体**部分**匹配）。

## 五、失败分析（评测器抓到的真失败）

策略层面没有失败；**实现层面有一条**：

| 用例 | 现象 | 处理 |
|---|---|---|
| `c203`（30 字节截断 ELF） | `fwmap` 报 `not_elf`，`stdlib` 报 `truncated` | 判定 fwmap 分类有误 → 修 `elf.py` 后两边都 3/3 |

这条失败的意义：**评测器能区分实现，即使区分不出策略**。
报告里**必须**把"实现区分度"和"策略区分度"分开写，否则会用一个 3/3 掩盖"三个策略都满分"。

## 七、重算说明（另一位读者怎么复核）

```bash
# 0) 环境：Python 3.11+，不需要固件 / GPU / 模型服务（模型组除外）

# 1) 归档复算（第 7 节 #1-#4）
python -m fwbench archive lab/recordings --expect 5,5,0

# 2) 从已落盘运行重算（仓库自带运行目录）
python -m fwbench report bench/runs/2026-11-28/fb-dev-rule --oracle bench/oracle/dev.json
python -m fwbench report bench/runs/2026-11-28/fb-holdout-rule --oracle bench/oracle/holdout.json
python -m fwbench report bench/runs/2026-11-28/fb-m --oracle bench/oracle/dev.json

# 3) 跨工具对照
python -m fwbench compare bench/runs/2026-11-28/elf-fwmap \
    bench/runs/2026-11-28/elf-stdlib --oracle bench/oracle/elfmeta.json --out runs/cmp

# 4) 评测器自身的测试
python tests/test_fwbench.py      # 39 项
```

运行目录里 `events.jsonl` 是事实来源，`report.md` 与 `summary.json` 由同一份汇总对象渲染。
