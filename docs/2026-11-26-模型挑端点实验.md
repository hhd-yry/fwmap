# 实验：端点由谁挑 —— 固定顺序 vs 模型自选

> 日期：2026-11-26　目标：DIR-615 C2 3.03（MIPS BE，专用 `sbin/httpd`）
> 对应论文：5.x「模型在端到端流水线中的职责边界」

## 一、要回答的问题

端到端流水线里，「先探哪个端点」这一步，交给模型做，和按固定顺序做，差在哪？

这个问题前面一直答不了：`probe` 虽然写在 agent 循环的动作白名单里，但探针从没接上
（`_execute` 里恒为 `None`），模型选了也只会得到一句「没有可用的固件探针」。
所以过去所有"模型参与"的说法，在这一步上都没有证据。

本次把 `probe` 真正接到固件前面，并跑了两组对照。

## 二、设置

| 项 | 值 |
|---|---|
| 固件 | DIR-615 C2 3.03（`sbin/httpd`，MIPS BE） |
| 候选来源 | `pages` 扫网页表单 → 36 条候选 |
| 预算 | 6 步（2 步取候选 + **4 次 probe**），两组完全相同 |
| 模型 | Qwen2.5-Coder-1.5B-Instruct，宿主机 4060 上跑（`fwmap serve`） |
| 固件侧 | VM 里 qemu-user + chroot 起 httpd，三对照判定（负对照/正对照/候选） |
| 连接 | SSH 反向隧道：VM 的 `127.0.0.1:11434` → 宿主机的 `fwmap serve` |
| 对照组 | `--no-llm`，固定顺序：pages → routes → 按抽取顺序逐条探 |

判定口径沿用 `routes.classify`：候选响应与负对照（随机 12 字母路径，248 B）显著不同
→ `handler`；与负对照一致 → `not-found`；0 字节 → `unknown`（服务没应答）。
正对照用 `GET /`（1818 B），每次探测前都重新采一次，用来区分「服务没起来」和
「这个端点把服务打死了」。

## 三、结果

### 3.1 探了哪几条

| 次序 | 固定顺序（无模型） | 结果 | 模型自选 | 模型给的理由 |
|---|---|---|---|---|
| 1 | `/apply.cgi` | handler | `/apply.cgi` | 有名字像表单目标的 |
| 2 | `/online_firmware_check.cgi` | handler | **`/login.cgi`** | **带有提交按钮和登录表单** |
| 3 | `/log_first_page.cgi` | handler | `/save_log.cgi` | 带参数的提交入口 |
| 4 | `/log_last_page.cgi` | handler | `/online_firmware_check.cgi` | 有名字像表单目标的 |

### 3.2 命中与代价

| 指标 | 固定顺序 | 模型自选 |
|---|---|---|
| handler 命中 | **4 / 4** | 3 / 4 |
| unknown（服务被打死） | 0 | **1** |
| 探到 `/login.cgi` 需要几次 | ≥ 14（它在 36 条候选里排第 14） | **2** |

`/login.cgi` 的响应是 **0 字节**，而同一轮的负对照返回 248 B、正对照返回 1818 B ——
服务在前两条请求时还活着，是 `/login.cgi` 把它打死的。这不是"没找到"，是崩溃。

## 四、怎么读这个结果

**不能说"模型更准"。** 固定顺序的 handler 命中率更高（4/4 对 3/4），因为它沿着
抽取顺序把"活着的页面"挨个扫了一遍；模型挑的那条把服务打死了，按 handler 口径算
是"没命中"。

**能说的是两件事做得不一样：**

1. **固定顺序擅长穷举，模型擅长跳着找异常。** 要够到第 14 条，固定顺序得先探
   13 条无关的；模型在 4 次机会里第 2 次就够到了，而且是靠"带提交按钮"这个可
   说出口的理由，不是随机。
2. **模型的代价是可能把目标打崩。** 它挑中的那条恰好是会把 httpd 打死的端点。
   对挖掘来说这是好事（说明挑得准），对"先把服务摸清楚再动手"的流程是坏事。
   → 这就给流水线提了个要求：**探测顺序要允许"先探最可疑的"**，而不是"先探最安全的"。

## 五、边界（不要过度解读）

1. 单个固件、单个版本、单次运行（n=1），不构成统计结论；
2. 模型只有 1.5B。7B 是否也能挑、挑得是否更好，没测；
3. 「模型自选」是**受限决策**：阶段由规则收束（先 pages、再 routes，然后才轮到挑），
   模型只在收束后的候选清单里选。这不是"模型自己决定整个流程"——
   实测让 1.5B 自由选动作，它连跑 6 步一次都没选过 `probe`，全被规则兜底。
4. `/login.cgi` 崩溃本身是候选漏洞（见 `漏洞报告-DIR-615-login-cgi-未认证崩溃.md`），
   本次实验只证明"模型挑中了它"，不改变它的证据等级。

## 六、复现

```bash
# 宿主机：把模型挂成 OpenAI 兼容接口
python -m fwmap serve --port 11434

# 反向隧道（VM 的 sshd 监听 11434，转发回宿主机）
python tmp/llm_tunnel.py

# VM：有模型
cd /home/ubuntu/fwmap-run
FWMAP_LLM_ENDPOINT=http://127.0.0.1:11434/v1 \
  python3 -m fwmap plan $ROOT/sbin/httpd --rootfs $ROOT --arch mips \
  --max-steps 6 --probe --json /tmp/plan-d615.json

# VM：对照组
python3 -m fwmap plan $ROOT/sbin/httpd --rootfs $ROOT --arch mips \
  --max-steps 6 --no-llm --probe --json /tmp/plan-d615-nollm.json
```

看 `trace` 里的 `source` 字段：`model` 是模型挑的，`heuristic` 是规则兜底的。
两者必须分开统计 —— 混在一起会把规则的功劳算到模型头上。
