# A 组对比：人工那一发 vs 工具那一发（2026-11-25）

> 目的：为什么同样字段、同样载荷，**人工发能执行、`fwmap dyn` 发不能**。

## 一、先把两份请求拿出来比

| 项 | 人工 | 工具 |
|---|---|---|
| 字段数 | 15 | 19 |
| 载荷 | `00:11:22:33:44:55'$(echo AB-PROOF >/tmp/fwmap_AB)'` | **完全相同** |
| 提交页 | `inter_wisp.asp` | **相同**（工具自己选中的） |

字段差异只有四处，且都不是关键：

```
只在工具里： wisp_fieldset / wisp_form / selSurvey / width（都是空值）
值不同：     stadrv_WPA2pskkey（12345678 vs admin12345）
             supportAllSecurity（'' vs '0'）
```

## 二、然后把两份都真的发出去

```
人工:  1523B  no-crash  证据=有（AB-PROOF）
工具:  1523B  no-crash  证据=有（AB-PROOF）
```

**两份都能执行。** 也就是说：**请求内容没有问题，差异不在载荷、不在字段。**

## 三、那问题在哪

把工具真实落盘的那 421 字节 body 拿去单独发，四种组合全部执行成功：

| 变体 | 响应 | 证据 |
|---|---|---|
| Host 带端口 + 认证 | 1523B | 有 |
| Host 不带端口 + 认证 | 1523B | 有 |
| Host 带端口 + 无认证 | 1523B | **有**（这个接口居然不校验认证） |
| Host 不带端口 + 无认证 | 1523B | 有 |

**但同一条 body 在 `fwmap dyn` 里发出去，返回 0 字节。**

## 四、已排除的原因

| 怀疑 | 结果 |
|---|---|
| 载荷形式 | 排除（完全相同） |
| 字段缺失 | 排除（多 4 个空字段不影响） |
| 值不对 | 排除（改值后仍能执行） |
| Host 带端口 | 排除 |
| 认证头 | 排除 |
| `--port` 默认 8080 | 已修（自动回落 80） |
| 会话复用 | 排除（换新会话仍 0B） |
| 残留服务占端口 | 排除（先 `_kill_guest` 再起） |

## 五、结论（诚实版）

**请求是对的，发的时候坏了。**

`fwmap dyn` 在跑完「对照组 + 若干发被拒请求」之后，再发这一发就拿到 **0 字节**——
服务端主动关了连接。这说明问题在**服务实例的状态**，不在我们的请求内容。

下一步三条（按成本排）：

1. **每发请求都用独立进程**跑一次（最笨但最稳，能立刻验证这个判断）；
2. 找出 Boa 在什么条件下开始关连接（看它的日志、连接数、fork 限制）；
3. 换更稳的模拟环境（FirmAE / 全系统），这条路本来就在计划里。

## 六、这轮顺带修掉的真问题

| 问题 | 影响 |
|---|---|
| `--port` 默认 8080，Boa 只认配置里的 80 | 所有请求 `no-listener`，看起来像固件不响应 |
| Boa 守护化（父进程 exit 0）被当成启动失败 | 永远等不到端口 |
| 端口 TIME_WAIT → 后续 bind 失败 | 探针/动态验证全线 `no-listener` |
| 三个页面字段混发（110 个） | 处理器直接拒绝 |
| 模板值 `<% getInfo(...) %>` 塞进表单 | 处理器拒绝 |
| MAC 类参数没前缀 | 注入到不了拼接点 |

**这六条每一条都会让工具把"打不中"误报成"没漏洞"。**
