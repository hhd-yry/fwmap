### E1 的依据

### E2 的依据

> CVE-2026-12810：*Edimax BR-6478AC V2 1.23 … function mp of the file /goform/mp …

同样五项全对。我们观察到的是崩溃（SIGSEGV），公告描述的是命令注入——
同一处入口，不同表现，**仍然算已公开**。

### D2 为什么值得留意

`html_response_page` 在离线库里 0 命中，DIR-615 C2 的 `apply.cgi` 也没有相关记录。
但它是**静态链**：只证明了"参数流进 sprintf"，没有动态证据。
而且 DIR-615 的 `apply.cgi` 需要登录，我们的 `login.cgi` 在 chroot 里跑不起来。
所以它既不能算发现，也不能算漏洞——**只能写"待验证"**。

## 三、这次查重的意义（写论文时用）

1. **把"复现"和"发现"分开了**：之前口头说"挖到了 Edimax 命令执行"，
   严查后是 CVE-2026-10127 的复现。论文里必须这么写，否则会被评审打回。
2. **证明查重是必要的一步**：如果没有这一步，很容易把复现当成发现——
   两条结果都命中了同型号同版本的 CVE，误判风险 100%。
3. **留下一个真正的候选**：D2（DIR-615 的 `html_response_page`）在库里没有记录，
   如果能解决登录问题并打出崩溃，就是一个"未报告目标上的确认"。
